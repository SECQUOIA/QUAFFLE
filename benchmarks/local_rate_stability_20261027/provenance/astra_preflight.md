**Nonblocking — Check the validation evaluation schedule when reusing a fit** <!-- gh-review-pr:finding=historical-validation-schedule -->

Location: `scripts/run_local_rate_stability.py:148–154`, in `audit_record`.

The audit requires every epoch in the history and verifies the best recorded validation checkpoint, but it does not require validation evaluations to occur on the planned schedule. The runner fixes `eval_every=2`; an otherwise compatible historical run evaluated every epoch can therefore pass and receive more checkpoint-selection opportunities than the new cells. A missing planned validation evaluation is likewise not rejected when it does not change the winning record.

I confirmed this by copying an actual historical record in memory, adding an epoch-1 validation entry, and calling the current `audit_record`: it accepted the modified record. I also independently checked that **all eight intended historical records already use exactly epochs 0, 2, …, 60**, so this does not invalidate those inputs or block the proposed experiment.

Remedy: compare the history's evaluated epochs with the exact planned set/order derived from `args.eval_every`, including epoch zero and the final epoch. Add tests that reject an extra evaluation and a missing scheduled evaluation while leaving the selected checkpoint otherwise valid. This is a bounded metadata check and needs no retraining.
